## B1 sequence, after named target authorization

1. Run `node scripts/mac-vm-preflight.mjs` on the authorized ARM64 Mac. This only observes OS/toolchain information. Standard CI may build/test the Swift package; it does not start a VM or establish a user-device grant.
2. Approve one exact source/size/digest/license record in trusted Core configuration. Use the existing `DownloadManager` with signed `raw-bootstrap-v1`, trusted publisher key, `bootstrapSources` pin, and either `HTTPSBootstrapSource` (bounded ranges, no redirects) or `LocalBootstrapSource` for an explicitly selected local copy. Same operation, source signature, target architecture, streaming digest verification and inert atomic activation remain mandatory. Catalog activation does not execute or boot the artifact.
3. For ISO media, `node scripts/verify-bootstrap.mjs /approved/path.iso` only verifies the pin. For the preinstalled cloud image, `node scripts/prepare-vm-disk.mjs --apply /protected/preparation.json /approved/cloud.img` verifies the source and an explicitly approved qemu-img binary digest, converts to a new raw disk, and resizes only that new disk. It does not install qemu-img, download anything, start a VM, or provision the guest. Its protected JSON requires targetId, expiresAt, action=`prepare-disk`, operationId, root, destination, diskBytes, qemuImg, qemuImgSHA256. Existing destination or interrupted staging refuses; review only that operation's `an-prepare-<operationId>` directory before retry. Never clean unrelated user data.
4. Prepare the Ubuntu guest disk in an expressly authorized installation/build environment. Install the pinned Node 24 runtime and admitted Codex 0.159.2 binary via their own verified official material, plus Ubuntu's signed bubblewrap, Python 3, systemd and bpftool packages. Record exact package versions/digests in the resulting private image manifest. These guest installation operations are NOT_RUN in A3; there is no claim that the raw cloud image already contains AN or Codex. Do not transfer host Home, SSH keys, auth caches or Core DB. A fully unattended first-boot guest installer is not supplied here; use an authorized image preparation process and retain its evidence before starting the helper.
5. Install the compiled guest entry and enforcement gate in a root-owned, Bot-inaccessible `/opt/an/node/`; the gate is `apps/node-agent/src/enforcement-gate.mjs`. The optional legacy `candidate-probe.mjs` primitive returns untrusted stdout only. It is not a trusted verifier: a malicious candidate can forge subprocess stdout despite pinning and isolation. A5's production verification adapter blocks that route and owns the separate trusted evaluator; no PASS claim may be derived from this primitive.
6. Create a private runtime rootfs that contains only public runtime files and empty mount points `/bot/home`, `/workspace`, `/proc`, `/dev`, `/tmp`, `/run`. Do not use the guest management root `/` as rootfs. Each Bot's private parent contains separate home/project/cache directories; Node's process registry and Runner SQLite/spool are outside all Bot mounts. Configure `NodeAuthority` with nodeId, sandboxId, generation, privateRoot, rootfsRoot, stateDirectory, expiring target actions, nativeRuntime `{version:'0.159.2',sha256:<actual installed binary>}`, and verifierProbeDigest where applicable. Runtime caches remain writable in Discussion; project is a real read-only mount. The fixed guest profile is botDirectory=`/bot`, HOME=`/bot/home`; CODEX_HOME and XDG directories are beneath it. Its exact clean PATH/LANG/TZ/HOME configuration matches A4 `codexBotEnvironment`. These guest-visible paths are separate from host/guest-management private storage paths.
7. Host authority JSON must be a regular owner-only `0600` file. It contains protocolVersion=1, nodeId, targetId, expiresAt (milliseconds), root (owner-only `0700` directory), allowed actions and an exact sandboxes map. Each sandbox specifies botId, private raw disk/EFI paths, optional pinned bootISO+bootSHA256, cpuCount, memoryBytes, diskBytes. `networkMode` defaults to none; NAT requires both networkMode=`nat` and `network-egress` action. EFI creation/disk allocation are reachable only through an authorized `create` request, never through preflight/tests. Record actual helper binary digest and the development signing/entitlement decision before launching it. Required entitlement: `com.apple.security.virtualization`; no signing certificates, notarization or system protection changes are automated.
8. Build the guest entry with `npm run build`, install `build/guest-node.cjs`, `scripts/start-guest-node.mjs` and the fixed enforcement gate in the approved guest, then run `node scripts/start-guest-node.mjs --apply /protected/guest.json`. `P1GuestConfiguration` defines the private listen config, Runner directory, Bot/project/Connection/Grant scope, expiry, admitted actions, NodeAuthority and SandboxPolicy; only this entry composes `GuestRuntimeRegistry`, authenticated approval/spool channel, actual attestation, graceful terminal EOF and trusted cgroup stop. Its protected listen config contains socketPath under `/run/an-node/`, keyPath, channel binding and expiresAt. Socket parent is owner-only `0700`, socket `0600`, key file protected `0600` JSON `{keyBase64:<32-byte key>}`. Key generation/transfer is a private B1 setup step, not catalog content. The A2 `GuestRuntimeRegistry` owns guest Runner/Driver/bundles; its approval port uses `serveNodeChannel(...).approvalPort(binding)` to call the sole Core approval service. No guest Core DB exists.
9. Run the protected `apps/node-agent/src/vsock-bridge.py /protected/bridge.json` in the guest. Its config contains targetId, port=47001, nodeSocket (the private Node socket). It accepts only host CID and forwards bytes; it does not launch CLI or decide authorization. The host helper's `connect` attaches VZ vsock and supplies a private same-user Unix socket. `connectNodeChannel` connects to that socket with the private key and exact Node binding. The protocol exchanges fresh signed nonces and authenticates bounded frames with sequence/binding checks; socket connectivity itself is not Runner readiness.
10. With protected `accountless-probe`/sandbox authority, use the guest Driver's fixed-version `initialize` through the authenticated channel. The standalone `accountless-node-probe.mjs` intentionally reports prerequisites/BLOCKED and never silently launches a host CLI. `initialize` is not a turn, login, model call or auth-ready result. Before real tasks, trusted Core must observe current environment/Runner/runtime/auth and the selected Connection/Grant separately.

## Actual enforcement and limits

`NodeController` starts only managed `an-<full-binding-sha256>.service` units. The fixed gate runs inside the final cgroup and reads memory, PID and CPU controls before `execve` of bwrap. Bwrap unshares namespaces, clears environment/capabilities, mounts only approved private paths and cannot see management sockets or registry files. Failed bwrap/user namespaces never fall back to host execution.

Network none uses a separate network namespace. The optional gateway path is explicitly **IP-address-level**, not a domain/port/per-request promise: approved exact IPs become systemd `IPAddressDeny=any` / `IPAddressAllow` cgroup BPF policies. The pre-execution gate requires actual ingress and egress BPF attachments and matching systemd policy readback. Missing bpftool/BPF or mismatch blocks before user argv. DNS and other addresses are not silently allowed. A finer gateway protocol, URL or port policy needs an additional tested gateway; an IP allowlist must not be described as request authorization. Per-Bot filesystem quotas are unsupported and requests for diskBytes fail; the VM raw disk bounds total capacity.

Stop writes only the tracked cgroup's `cgroup.kill`, then observes recursive cgroup.events. Parent exit alone does not release a writer. If exit status is unavailable but containment is empty, the observation is isolated, not successful exit. Actual systemd execution results and full binding mappings persist in Node's private journal. Missing/corrupt/unknown evidence stays blocked.

Task completion never calls Provider.destroy. Stop preserves disk/home/project/cache. Destroy retires the binding; deleting data is a separate operation. Helper crash within the same host boot remains UNKNOWN; only a different kernel boot-session UUID proves all previous local VMs stopped and permits cold-start recovery with a new generation. This limitation remains explicit in B3. Shutdown of private bridges waits for copy-worker retirement before closing descriptors.

## Current runtime and installed-state attestation

After actual Driver initialization, `NodeController.attestNative(binding, trustedPolicy)` reads the exact native process record, pinned executable identity, recursive cgroup membership and controls, namespace separation, private mount inodes and read-only flags, and the actual initial process environment. Gateway mode additionally reads current BPF attachments and exact systemd IP allow/deny configuration. Any missing/mismatched evidence rejects. `NodeRunnerChannel.attestRuntime(binding)` exposes this bounded observation through an injected trusted callback; request messages never provide policy. This implementation has refusal/contract tests only; actual OS positive controls remain B1/B2 NOT_RUN.

`BotProvisioner.adoptInstalled(operationId, expectedSandboxRef, verifyInstalled)` clears prior readiness, obtains fresh live running helper observations before and after the trusted installed-file/Node validation callback, and advances the same durable record's generation/environment only when they agree. An expected generation in protected config is not evidence. The callback must validate actual installed artifacts and the current Node attestation. Runtime, Runner and auth readiness remain separate later observations; stale Core readiness does not become live automatically.

For validated native `turn/completed`, A2 guest registry calls `NodeController.finishNative(binding)`: close only that exact app-server stdin, wait at most five seconds for real close, then observe the whole cgroup. EOF is not proof of success; no kill or exit-code synthesis occurs. A6 Core completion still requires fresh trusted stop and verification evidence.
